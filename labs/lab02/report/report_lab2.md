\# Введение

\#\# Актуальность

Системы контроля версий (VCS) являются стандартом разработки программного обеспечения и ведения проектной документации. Владение инструментарием Git, настройка защищённого криптографического взаимодействия с удалённым сервером через SSH и обеспечение целостности коммитов посредством GPG-подписей — фундамент безопасной и прозрачной командной и индивидуальной разработки.

\#\# Цель работы

Изучить идеологию и применение средств контроля версий, а также освоить практические навыки по работе с системой Git, генерации ключей авторизации и организации рабочего пространства проекта.

# **Выполнение лабораторной работы**

## **1\. Установка программного обеспечения**

В терминале виртуальной машины под управлением Fedora Linux установили пакеты git и консольный клиент gh:  
sudo dnf install \-y git gh

## **2\. Базовая настройка Git**

Задали глобальные пользовательские параметры (имя автора, email, ветку по умолчанию master, корректное отображение UTF-8 и правила обработки окончаний строк для Linux):  
git config \--global user.name "Тимофей Бессонов"  
git config \--global user.email "mamkar228@yandex.ru"  
git config \--global core.quotepath false  
git config \--global init.defaultBranch master  
git config \--global core.autocrlf input  
git config \--global core.safecrlf warn

## **3\. Создание и настройка SSH-ключей**

Для безопасной авторизации на GitHub без постоянного ввода пароля сгенерировали SSH-ключи:  
\# Генерация RSA-ключа длиной 4096 бит  
ssh-keygen \-t rsa \-b 4096 \-C "mamkar228@yandex.ru"

\# Генерация современного ключа Ed25519  
ssh-keygen \-t ed25519 \-C "mamkar228@yandex.ru"

Скопировали открытый ключ id\_ed25519.pub и добавили его в разделе **Settings \-\> SSH and GPG keys** на GitHub:  
cat \~/.ssh/id\_ed25519.pub

\!\[\[02-ssh-github.png\]\] *Рис. 3\. Добавление открытого SSH-ключа в аккаунт GitHub*

## **4\. Создание GPG-ключа и верификация коммитов**

Сгенерировали GPG-ключ для криптографической подписи авторства коммитов:  
gpg \--full-generate-key

Параметры генерации:

> * Тип ключа: (1) RSA and RSA;  
> * Размер: 4096;  
> * Срок действия: 0 (бессрочно);  
> * Имя: Тимофей Бессонов;  
> * Email: mamkar228@yandex.ru.

Получили отпечаток (Fingerprint) созданного ключа и экспортировали его публичную часть в формате ASCII:  
gpg \--list-secret-keys \--keyid-format LONG  
gpg \--armor \--export \<FINGERPRINT\_ID\>

Публичный ключ был добавлен в GitHub (**Settings \-\> SSH and GPG keys \-\> New GPG key**). В настройках профиля был активирован режим **Vigilant mode** (пометка неподписанных коммитов меткой Unverified).  
Настроили Git на автоматическое подписание всех создаваемых коммитов:  
git config \--global user.signingkey \<FINGERPRINT\_ID\>  
git config \--global commit.gpgsign true  
git config \--global gpg.program \$(which gpg2)

\!\[\[03-gpg-setup.png\]\] *Рис. 4\. Настройка автоматической подписи коммитов с GPG*

# **Ответы на контрольные вопросы**

> 1. **Что такое системы контроля версий (VCS) и для решения каких задач они предназначаются?** Система контроля версий (VCS) — это программное обеспечение, регистрирующее изменения в одном или нескольких файлах с течением времени, позволяя возвращаться к определённым версиям, отслеживать историю правок, авторов изменений и эффективно объединять совместную работу нескольких участников без риска потери данных.  
> 2. **Объясните следующие понятия VCS и их отношения: хранилище, commit, история, рабочая копия.**  
   * **Хранилище (Repository):** база данных проекта, содержащая все файлы, каталоги и метаданные обо всех когда-либо сделанных ревизиях (в Git — каталог .git).  
   * **Рабочая копия (Working Directory):** извлечённый из репозитория текущий срез файлов на диске, доступный пользователю для чтения и модификации.  
   * **Commit (коммит / фиксация):** снимок состояния индексированных файлов в определённый момент времени с фиксацией автора, даты и комментария.  
   * **История (History):** направленный граф (цепочка) последовательных коммитов от начального состояния проекта до текущего момента.  
> 3. **Что представляют собой и чем отличаются централизованные и децентрализованные VCS? Приведите примеры.**  
   * **Централизованные (CVCS):** вся история хранится на одном выделенном сервере (клиенты скачивают только рабочую копию). При отказе сервера работа с историей блокируется. Примеры: CVS, Subversion (SVN).  
   * **Децентрализованные (DVCS):** каждый пользователь имеет полную локальную копию всего репозитория с полной историей изменений, что позволяет работать автономно без сети и совершать коммиты локально. Примеры: Git, Mercurial, Bazaar.  
> 4. **Опишите действия с VCS при единоличной работе с хранилищем.**  
   1. Инициализация репозитория (git init) или клонирование.  
   2. Редактирование, добавление или удаление файлов в рабочей директории.  
   3. Проверка статуса изменённых файлов (git status).  
   4. Добавление нужных изменений в индекс (git add).  
   5. Фиксация изменений осмысленным коммитом (git commit \-m "...").  
   6. Периодическая отправка на удалённый сервер для резервного хранения (git push).  
> 5. **Опишите порядок работы с общим хранилищем VCS.**  
   1. Получить актуальные изменения с сервера в базовую ветку: git checkout master и git pull.  
   2. Создать новую тематическую ветку для фичи: git checkout \-b feature-branch.  
   3. Выполнить работу, зафиксировать коммиты (git add, git commit).  
   4. Подтянуть возможные новые изменения с мастера и разрешить конфликты (merge/rebase).  
   5. Опубликовать ветку на сервере (git push origin feature-branch).  
   6. Оформить запрос на слияние (Pull Request / Merge Request), пройти ревью и выполнить слияние в основную ветку.  
> 6. **Каковы основные задачи, решаемые инструментальным средством Git?**  
   * Полное отслеживание и сохранение истории всех файлов проекта;  
   * Быстрое и гибкое ветвление и слияние независимых линий разработки;  
   * Обеспечение криптографической целостности данных (хеши SHA-1/SHA-256);  
   * Поддержка полностью автономной локальной работы без постоянного подключения к сети.  
> 7. **Назовите и дайте краткую характеристику командам Git:**  
   * git init: инициализация нового локального репозитория;  
   * git clone: клонирование существующего удалённого репозитория;  
   * git status: вывод состояния рабочей копии и индекса;  
   * git add: добавление файлов в область подготовки (индекс);  
   * git commit: создание точки сохранения (коммита);  
   * git log: просмотр истории коммитов;  
   * git branch: просмотр, создание и удаление веток;  
   * git checkout / git switch: переключение между ветками или ревизиями;  
   * git merge: слияние одной ветки в текущую;  
   * git pull: получение изменений из удалённого репозитория и их слияние;  
   * git push: отправка локальных коммитов в удалённый репозиторий.  
> 8. **Приведите примеры использования при работе с локальным и удалённым репозиториями.**  
>    \# Локальная работа  
>    git init my-project  
>    cd my-project  
>    echo "Initial data" \> file.txt  
>    git add file.txt  
>    git commit \-m "Initial commit"

>    \# Связывание с удалённым репозиторием и отправка  
>    git remote add origin git@github.com:username/my-project.git  
>    git branch \-M master  
>    git push \-u origin master

> 9. **Что такое и зачем могут быть нужны ветви (branches)?** Ветвь — это подвижный указатель на конкретный коммит в дереве проекта. Ветвление позволяет изолировать разработку новой функциональности, проведение экспериментов или исправление ошибок от стабильного кода в главной ветке (master/main). Несколько разработчиков могут одновременно работать над разными ветками, не мешая друг другу.  
> 10. **Как и зачем можно игнорировать некоторые файлы при commit?** Игнорирование настраивается через файл .gitignore, куда построчно заносятся маски и имена исключаемых файлов. Это необходимо для того, чтобы случайно не фиксировать в репозитории временные системные файлы, кэши, бинарные файлы компиляции, дампы памяти, а также файлы, содержащие секретные токены и пароли.
